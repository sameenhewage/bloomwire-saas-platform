1.Ownership statement

  • Bloomwire is a WhatsApp-first SaaS product built on the WhatsWay / Chatwoot-derived OSS base.
  • Bloomwire customizations are Bloomwire-owned, layered on top of the OSS code path.
  • Chatwoot Enterprise code/features are not used. Bloomwire runs with DISABLE_ENTERPRISE=true.
  • Current channel scope is WhatsApp only. Future channels may be added later; the current implementation is intentionally WhatsApp-first and must not be over-built for multi-channel now.
  • Bloomwire behavior is gated behind Bloomwire Mode (BLOOMWIRE_MODE_ENABLED); with Mode OFF, behavior is intended to stay stock-compatible.

3.Phase-by-phase implementation log

Phase 13B — WhatsApp production hardening Completed

  • Encrypt the WhatsApp provider config at rest when AR encryption keys are configured (target: no plaintext token-at-rest; degrades safely if keys absent).
  • Outbound retry for transient send failures.
  • Configurable Graph API version (no hard-coded Meta API version).
  • No Enterprise dependency.

Phase 13C — Live Meta certification (dev) Completed templates parked

  • Validated on the live dev environment; webhook callback verified.
  • Inbound/outbound WhatsApp session chat verified; status lifecycle verified (sent/delivered/read).
  • Templates parked — no approved WABA template available to certify the template path.

Phase 13D — Webhook PII log hardening Completed

  • Disabled risky job-args logging for WhatsApp-related jobs.
  • Deep-filtered webhook entry payloads from request-param logs.
  • Prevents phone / profile / wa_id / secrets from leaking into logs (via config.filter_parameters + log-level adjustments; logging-only).

Phase 13E — Template / out-of-window parking Parked

  • Template send parked until an approved WABA template exists.
  • Session chat works; the template path waits on Meta/WABA readiness.

Phase 14 — Customer provisioning foundation Completed PR #68 · #69

  • Onboarding runbook authored.
  • Secure Ops credential capture — provider credentials handled under a filtered provider_config key; never echoed.
  • Customer provisioning orchestration (Bloomwire::CustomerProvisioningService): account → owner → agents → WhatsApp channel → inbox, and attaches provisioned agents to the WhatsApp inbox (attach_agents_to_inbox).
  • No Meta live registration unless explicitly authorized.

Phase 15A — Platform-admin boundary Completed PR #71

  • /super_admin is the Bloomwire internal / platform console.
  • users.type = 'SuperAdmin' is a Rails/Devise STI identity only — not a business role.
  • Platform access is controlled by bloomwire_platform_admins (ADR-0007); only approved platform admins can access /super_admin.
  • Customer/business users are blocked from /super_admin.

Phase 15A.1 — Owner-only Platform Admin management Completed PR #72

  • Added the Platform Admins page; roles owner / admin / support.
  • Owner can create / grant / revoke (soft) / reactivate platform admins.
  • Last-owner guard (the only active owner cannot be demoted/revoked).
  • No accidental promotion of normal users.

Phase 15A.2 — Users vs Platform Admin flow consistency Completed PR #73

  • Users page preserved for normal/customer user creation.
  • Raw Type field hidden on forms and stripped server-side in Bloomwire Mode.
  • Users table shows computed Platform Access instead of raw Type.
  • Business users are normal users with account membership, not users.type.

Phase 15B — Business account-user flow clarity Completed PR #75

  • account_users.role = administrator displayed as Business Admin; agent displayed as Agent.
  • No BusinessOwner role added; DB values remain administrator / agent (display/UX clarity only).
  • Business/customer account access does not grant platform access.

Phase 15C — SuperAdmin impersonation token hardening Completed Issue #74 closed PR #76

  • Issue #74: the old user-show page rendered an sso_auth_token in the link href.
  • Impersonation changed to POST: token generated only on click, server-side; no token in rendered HTML/href; final browser URL has no token.
  • Handoff uses head + Location (not redirect_to) → token not in the Rails "Redirected to" log; also [FILTERED] from param logs. Token stays short-lived (5 min) + single-use.
  • Residual: the intermediate /app/login?…sso_auth_token=… handoff URL still exists briefly; full removal needs a separate frontend/auth handoff redesign.

Phase 15D — Assigned Agent RCA Not a bug RCA only

  • Classification: A (not a bug) + B (setup). Stock Chatwoot behavior — no code change.
  • Rule: assignable agents = inbox members + account administrators.
  • Settings → Agents shows account-level users; the conversation Assigned Agent dropdown uses the inbox-scoped assignable-agents endpoint.
  • The account Agent was not an inbox member → excluded; the administrator appeared because admins are always included.
  • Not caused by Bloomwire Mode or 15A/15B permission changes.
  • Correct no-code fix: add the agent as an inbox collaborator/member. Future onboarding must ensure selected agents are attached to the WhatsApp inbox (the provisioning service already does this).

4.Permission model reference

Platform side (Bloomwire internal)

  • Surface: /super_admin
  • users.type = 'SuperAdmin' = technical Devise/STI identity
  • Platform access controlled by bloomwire_platform_admins
  • Platform roles: owner, admin, support
  • Platform users are Bloomwire internal users

Business / customer side

  • Surface: /app/accounts/:id
  • Account membership controlled by account_users
  • Roles (DB): administrator, agent
  • UI labels: Business Admin, Agent
  • Do not add BusinessOwner yet; do not use users.type for business roles

Conversation assignment

  • Assignable agents = inbox members + account administrators
  • An account Agent must also be an inbox collaborator/member to appear in the Assigned Agent dropdown
  • Team assignment is separate from agent assignment; Priority is separate from both

5.WhatsApp architecture reference

  • Current scope is WhatsApp only.
  • Global webhook/router direction: one shared webhook entry resolving to the correct mapped channel/inbox. No per-customer random webhook strategy.
  • Provider credentials must not be exposed (filtered in logs; never in business-facing responses; scrubbed via privacy hardening).
  • No WhatsApp/Meta live calls unless explicitly authorized (tests stay WebMock-blocked).
  • No duplicate conversation/message source of truth — existing Chatwoot/Bloomwire data remains the single source of truth.
  • Future channels should not be over-built now.

6.OSS / Enterprise statement

  • Bloomwire uses the OSS-compatible code path only (DISABLE_ENTERPRISE=true).
  • Enterprise code/features are not part of the Bloomwire implementation and must not be relied upon.
  • No Enterprise dependency should be introduced.
  • Any future Enterprise-like feature must be implemented in Bloomwire-owned code, or evaluated legally/technically before any use of Enterprise-licensed code.

7.What we intentionally did NOT change

  • No BusinessOwner role yet (account roles remain administrator / agent).
  • No new customer message/conversation tables (no duplicate chat storage).
  • No Enterprise WhatsApp code usage.
  • No multi-channel support yet (WhatsApp-first).
  • No billing/subscription system yet.
  • No Meta template send until an approved template exists.
  • No full replacement of the Chatwoot assignment system — stock account/inbox assignment semantics preserved (Bloomwire onboarding should respect them).

9.Operational rules for future agents

  • Evidence first — no assumptions; prove the root cause before changing anything.
  • Do not merge/deploy without approval.
  • Exact-SHA review gate — only merge the explicitly approved head SHA; abort if it changed.
  • No WhatsApp/Meta/provider credential mutation unless explicitly authorized.
  • Mask secrets, tokens, phone numbers, and emails where practical.
  • Do not use users.type for customer/business roles.
  • Do not add BusinessOwner unless separately designed.
  • Do not duplicate chat/message storage.
  • Test Bloomwire Mode ON; test stock-compatible behavior (Mode OFF) when touching Chatwoot flows.

10.Documentation Governance

Introduced in Phase 15E.1. Canonical rule: AGENTS.md → "Bloomwire Documentation Governance".

Every Bloomwire-owned change must be transparent and documented — no hidden or undocumented changes. Any PR that changes behavior, permissions, security, onboarding, WhatsApp flow, APIs, UI flows, the data model, an operational process, or customer-facing behavior must update, in the same PR:

  • docs/bloomwire/implementation-ledger.md and docs/bloomwire/implementation-ledger.html
  • the Bloomwire change log (docs/bloomwire/change-log.md)
  • the related ADR/runbook if architecture or operations are affected

A PR that changes Bloomwire behavior without updating docs/changelog is not approval-ready. Docs-only PRs need no runtime deploy.

Each entry records: phase · PR number · merge SHA · what changed · why · what was intentionally NOT changed · validation evidence · residual risks / parked items. Security/permission/WhatsApp entries must also state: no secrets exposed · no provider-credential mutation unless authorized · whether any live Meta/WhatsApp calls were made · whether Enterprise code was touched.

Preserve the invariants: no users.type for business roles · no BusinessOwner without separate design · no duplicate chat/message source of truth · no Enterprise dependency · WhatsApp-first scope.

Definition of Done (Bloomwire change)

  • ☐ code implemented
  • ☐ tests passed
  • ☐ runtime/browser proof when applicable
  • ☐ docs updated (implementation ledger .md + .html)
  • ☐ changelog updated (docs/bloomwire/change-log.md)
  • ☐ residual risks recorded
  • ☐ exact merge SHA recorded after merge
